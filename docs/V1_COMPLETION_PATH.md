# Path to Dwindy v1 complete

2026-10-03. The acceptance target remains the existing project proposal: install
on an ordinary computer, run a compact local model, use standalone chat, configure
bounded local project knowledge, and integrate through the local API without a
mandatory cloud service or database server. No new milestone is created here.

A test failure blocks v1 when it demonstrates a broken accepted requirement.
For each failure, identify that requirement and its impact. Experimental quality
gates keep their historical outcomes; failing them does not introduce a new v1
requirement. Known model/retrieval limitations may remain documented limitations.
Privacy, security, corruption, broken lifecycle and serious architectural defects
remain blockers.

## Required before v1

1. Close existing end-to-end paths with ordinary integration tests: permitted local
   documents/project snapshot, indexing, discovery, admission, bounded original
   evidence, local conversation, actual supplied-source metadata, API and browser
   status. Verify existing metadata against the actual Core packet, independently
   of generated wording. Reuse the shipped paths; do not require a new framework
   or a new generic information-result abstraction merely to finish v1.
2. Practical Reach is now required by the amended v1 decision: one bounded Wikipedia
   request, disabled by default, deterministic acquisition/admission/actual-supply status,
   source identity and graceful local fallback. H2 remains preserved/deferred; its response
   quality gates are not v1 acceptance gates. Use ordinary tests and the five approved live
   checks, then return directly to final assembled-runtime verification.
3. Complete the existing hardening/release checks: documented clean installation,
   offline conversation and local retrieval, reference-machine CPU/context limits,
   authentication and allowed-origin behavior, persistence on/off, restart/reset,
   cancellation/rollback, manual snapshot update/deletion, and graceful unavailable
   states. Fix demonstrated requirement defects, then rerun affected checks.
   These are release checks, not claims that new defects have already been found.
4. Reconcile user-facing capability/limitation documentation and the release
   checklist. Describe source metadata as actual information flow, not verified
   grounding. State that host context is information, no host-action executor is
   provided, semantic matching is not adopted, and practical optional Reach reports actual supply.
   Keep the independent standalone connection fix. Inventory remaining requirement
   defects and close them before declaring v1 complete.

Existing M12 optimization/v1 hardening is the place for this work. Do not reopen
M11 semantic policy or turn a failed experimental gate into a new release gate.
Qwen remains the interchangeable conversational generation layer. Dwindy enforces
source permissions, budgets, lifecycle and reports source/status facts through
system outputs; it does not need Qwen to verbalize them correctly.

## Optional after v1

- Further semantic retrieval only if separately justified/approved; this bounded
  development experiment is not adopted. Lexical limitations are acceptable for v1.
- Additional file formats, broader multilingual coverage and interface polish when
  they serve a measured product need. None is a new prerequisite for release.

## Research or future work

Arbitrary semantic conflict recognition/resolution, assistant-history fact repair,
perfect attribution/partial-support reasoning and answer self-consistency remain
model limitations/research. M11 and Foundation were not adopted as complete
response policies; their holdouts remain unspent. Larger model/encoder comparisons,
autonomous exploration and training are not automatic follow-up milestones.

The next engineering step is an ordinary v1 integration/release gap check against
accepted requirements, followed by fixes only for demonstrated gaps.
